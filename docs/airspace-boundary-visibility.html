二、什么算「有管制」

边界数据本身不带管制状态，需要按当时在线的 VATSIM 席位反推：

FIR / UIR
取席位呼号的航路席位（末段为 CTR 或 FSS），且前缀命中该 FIR 的 id。
例：ZBPE_CTR → 点亮 ZBPE；ZBPE_N_CTR → 点亮 ZBPE；ZBPE_FSS → 点亮 ZBPE。
APP / TRACON
沿用原有的扇区匹配：席位前缀命中扇区 prefix，且后缀为 APP。
APP / TWR / GND / DEL 不算有航路管制。这些席位只管机场周边，不足以代表整个 FIR。 因此 ZSSS_APP、ZBAA_TWR、ZBAA_GND、ZSSS_DEL 都不会点亮 FIR 填充 （已用真实数据验证，见第五节）。

五、验证

用真实数据验证，不是推理。 抓取 Volanta boundaries.json（1097 个要素 / 1091 个唯一 id）与 VATSIM 实时快照（156 个在线席位）， 用 Python 复刻判定逻辑逐例核对。
  • tsc -b → 0 error；vite build → 成功（9.56s）
  • 实时点亮 13 个 FIR id，含 ZBAA_CTR → ZBAA 及其 5 个 ZBAA-* 子分区、WAAF_CTR → WAAF 及 9 个子分区
  • 14 个构造用例全部通过；混合场景通过；无席位在线 → 点亮 0 个（FIR 不出填充）
  • 反例确认：ZSSS_APP / ZBAA_TWR / ZBAA_GND / ZSSS_DEL 均不点亮
  • 中国区数据集含 52 个 Z 开头 id，主要 FIR（ZBPE ZGZU ZHWH ZJSA ZLHW ZPKM ZSHA ZUUU VHHK）均在列

六、取舍与边界

  • FIR 填充色未改：仍是 #ffffff @ 0.018，只加了过滤。这个不透明度极低，肉眼仅在大片区对比时能察觉。若希望「有管制」一眼可辨，可与 APP 统一为 #00c96b，或提高不透明度。
  • 子分区联动条件：只有当席位前缀与母边界完全同名时才联动（如 ZBAA_CTR → ZBAA-E）。若由更上层席位（如 ZBPE_CTR）管制，子分区不会点亮。
  • 数据延迟：管辖状态依赖 VATSIM 快照，按 15 秒轮询刷新，因此边界填充会随之变化 —— 这是预期行为。
  • 不可本地运行验证：本机缺少 Rust 工具链（cargo 不在 PATH），npm run tauri dev 无法启动，所以上述结果是逻辑与构建层面的验证，未做真机视觉确认。
