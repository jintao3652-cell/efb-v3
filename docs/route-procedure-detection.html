为什么 CIND8S / ROKI1B 没有被识别成进离场程序

EFB V3 · 2026-09-11 · 计划 DLH106 EDDF → EDDM · 结论：代码里从来没有「把航路文本解析成程序」这一步

一、你的这条计划实际存成了什么

-- %APPDATA%\SkyBoard EFB\skyboard.db
callsign : DLH106 | EDDF -> EDDM
route    : CIND8S CINDY Z74 HAREM T104 ROKIL ROKI1B
RWY      : dep=None arr=None
sid      : (NULL)
star     : (NULL)
approach : (NULL)

sid / star 三个字段全是空的 —— 不是匹配失败，是根本没被写入过。

二、根因链

  1. 计划里 route 是纯文本字段，sid / star 是另外的独立字段，两者之间没有任何桥
  2. CIND8S / ROKI1B 是程序标识符，不是航路点 —— SimBrief 的 navlog 里这两个 fix 压根不存在， 所以连 route_points 里都不会出现它们
  3. 全项目搜下来，plan.route 只被用在两处：列表里显示、编辑框里编辑。 没有任何一处把它切开去反查程序表
  4. SimBrief 导入那条链路里，构造 FlightPlan 时没有带 sid / star， 即使 SimBrief 侧知道，也会在这一步丢掉
  5. 后端 save_flight_plan 只是原样落库，同样不做解析
  6. 结论：sid / star 只可能来自编辑器的下拉手动选择； 自动识别这个功能从来没有被实现过

从你本机的 Fenix 导航库 C:\ProgramData\Fenix\Navdata\nd.db3 直接查：

四、修复

新增纯函数模块 src/lib/route-procedures.ts，按飞行计划格式的通用约定识别：

// SimBrief 等主流格式的约定：首个元素是离场程序名，末个元素是进场程序名
CIND8S CINDY Z74 HAREM T104 ROKIL ROKI1B
   ↓                                    ↓
 EDDF 的 SID 表                        EDDM 的 STAR 表
   ↓ 按名称精确匹配                       ↓ 按名称精确匹配
 CIND8S (ID 1161)                     ROKI1B (ID 36843)

然后在飞行计划编辑器里接上自动补全：

  • 程序表读回来之后，按航路文本补一次 sid / star
  • 只在对应字段为空时补，绝不覆盖手动选择
  • 按 (计划 id, 航路文本) 只补一次（useRef 守卫），不会反复触发
  • 不匹配就什么都不做 —— 比如首 token 是雷达引导后的第一个航路点时不猜
  • 选中时同时定跑道（procedureSelection），并把程序航迹点交给已有的取点流程

顺带把手动选择与自动识别统一到同一个 procedureSelection()，避免两处逻辑各自漂移。

六、副产品发现：跑道不指定时反而取不到 STAR 的点

ROKI1B 在 nd.db3 里的 leg 是按跑道过渡重复编码的（RW26L 两条、RW26R 两条）， 而后端取点时会用跑道过滤：

ROKI1B + 跑道 '26L' → 2 点      ROKI1B + 跑道 '08L' → 0 点
ROKI1B + 跑道 '26R' → 2 点      ROKI1B + 跑道 '08R' → 0 点
                                ROKI1B + 不指定   → 0 点

跑道为空时，normalize_runway("") 与 RW26L 对不上，leg 会被整批过滤掉。 所以自动识别顺带定跑道这一步不是锦上添花，而是拿到 STAR 航迹的必要条件。
